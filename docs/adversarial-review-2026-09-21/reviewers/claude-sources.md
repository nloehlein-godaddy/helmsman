## Summary

I did not find a reachable, exploitable domain-correctness bug in this area. The code is unusually defensive: nearly every mutation re-validates a `revision`/`stableJson` snapshot taken earlier in the same call, every pagination loop bounds page count and detects non-advancing/duplicate cursors, and every idempotency key (`(runId,attempt,eventId)`, `(sourceId,externalId)`, `(sourceId,displayKey)`, `admissionId`, `localRequestId`, `(caller,requestId)`) is checked against a content hash before being treated as a safe replay. I deliberately tried to break the "uncertain receipt" and "duplicate ID" invariants called out in my task brief and could not. Below are the concrete things I inspected, the negatives I verified by execution (not just reading), and a short list of low-severity observations/improvements. No production code was changed.

## Findings

**No confirmed bugs (high or medium severity) in domain/data correctness.** Everything below is either a verified negative (hypothesis disproved by code + test) or a minor/low-severity observation.

### Low-severity observations (not bugs, worth a maintainer's attention)

1. **`aggregateOutcomes` silently collapses duplicate `runId`s in its input array (last-write-wins), instead of rejecting them.**
   `server/helmsman/outcomes.ts:166-172` builds `selected` as a `Map<string, RunRow>` keyed by `run.id`; a later entry for the same id in the `input.runs` array silently overwrites an earlier one (different `status`/`costUsd` and all). Contrast this with `usage-service.ts`'s `reportsByRun`/dedup logic and `usage-store.ts`'s `recordUsage`, which both throw `UsageConflictError` on a mismatched duplicate rather than picking one silently. Verified by execution: `probes/claude_sources/outcomes-adversarial-probe.test.ts` ("duplicate run ids collapse via Map"). **Impact:** low — `aggregateOutcomes` is an internal aggregation helper fed by `db`-sourced run lists that should already be unique by primary key; I did not find a caller that can pass genuine duplicates today. Flagging as a latent inconsistency in defensive posture, not an exploitable path. **Suggested direction:** either explicitly document "last write wins by id" as intentional, or add the same conflict-on-mismatch check used for usage records, for consistency.

2. **Minor error-message wording nit shared by two window validators.** `server/helmsman/usage-service.ts` (`parseUsageQuery`) and `server/helmsman/outcomes.ts` (`aggregateOutcomes`, line 163) both throw `'Choose a window from one instant up to 366 days'` when `end <= start`. A zero-length window (`end === start`) is actually rejected too, so the message is slightly inaccurate (it should say "more than one instant" or similar). Purely cosmetic; not a logic bug — confirmed the actual bound math (`> 366 * DAY`) is correct in both places.

3. **Todos `localHistory`'s per-event top-K eviction (`src/plugins/todos/provider.ts:161-165`) re-sorts the entire buffered-events array on every push once `events.length > request.eventLimit`.** This is O(n log n) per insertion (bounded by `eventLimit ≤ 50` and 7 days × up to 100 records/page × 3 events, so practically small), functionally correct (verified: it always evicts the globally-oldest event, not a page-order artifact) but a legitimate small-object min-heap would be cheaper. Performance nit, not correctness.

### Verified negatives (hypotheses I tried to disprove and could not break)

All of the following were checked by reading the exact code path *and* confirmed with an executed test (either a pre-existing suite test I ran, or a probe I wrote in `probes/claude_sources/`):

- **Cross-source ID collision.** Duplicate `externalId` strings across two different `sourceId`s cannot cause identity confusion: every alias/claim/quarantine lookup in `server/helmsman/task-sources/store.ts` and `task-source-service.ts` keys or filters on `sourceId` in addition to `externalId`/`displayKey`. `src/plugins/todos/provider.ts`'s `ref()` helper also independently rejects any local record whose `ref.sourceId` doesn't match the calling instance, even when a malicious/buggy `local` adapter returns a record with the requested `externalId` but a foreign `sourceId`. Verified by probe (`todos-adversarial-probe.test.ts`, "cross-source id collision").
- **Malformed/stale provider pages and cursors.** Both `src/plugins/jira/provider.ts` and `src/plugins/todos/provider.ts` bound page count (100), detect a `nextCursor` that fails to advance or repeats, reject a page reporting a duplicate `externalId`, and reject a page containing an item outside the requested repo scope. Verified by probe: fed the Todos provider a `local.list()` stub that returns a non-advancing cursor forever, and one that returns a duplicate `externalId` in a single page — both correctly throw (`'did not advance'`, `'duplicate'`) instead of looping or double-counting.
- **Scope/identity changing mid-operation.** `task-source-service.ts`'s `context()` wraps every `local`/`http` accessor call in a `checked()` helper that re-runs `assertScope()` both before *and* after the async provider call, and `todosProvider`'s own `listLocalTasks`/`localHistory` independently snapshot `describeCollection()` before paging and re-check `collectionId`/`revision` equality afterward. Verified by probe: swapped `collectionId` between the pre- and post- `describeCollection()` calls inside `list()` and confirmed it throws `'Task collection changed; reload the list'` rather than returning a page built from an inconsistent snapshot.
- **Uncertain/outer-inner receipts (lost responses, retry, refresh).** `server/helmsman/source-command-coordinator.ts`'s `dispatch()` performs the local mutation (`options.local.applyCommand`) and the outer receipt transition to `'succeeded'` inside the *same* `commands.transaction()` call. Since `commands` (`SourceCommandStore`) and `local` (`LocalSourceAdapter`) are wired from the same shared `Persistence`/`better-sqlite3` connection at construction (confirmed in `server/helmsman/application.ts:334-357`, and in every test fixture), `persistence.transaction`'s nested-transaction handling (`server/helmsman/persistence.ts:66`, `sql.inTransaction ? sql.transaction(action)() : ...`) makes this a single atomic SAVEPOINT — the local mutation and the "succeeded" receipt can never partially commit relative to each other. When an error occurs whose outcome is genuinely unknown (e.g., not a definite `PersistenceConflictError`/`PersistenceValidationError`/provider rejection), the coordinator marks the command `'recovery-required'` rather than guessing; before doing so it always calls `reconcile()`, which checks `local.hasCommandResult(localRequestId)` directly against the *actual* mutation ledger (`source_commands` table) so a response that was lost on the wire but actually applied is detected and surfaced as `'succeeded'`, not silently dropped or double-applied on retry. I did not need to write a new probe here — the existing suite (`server/helmsman/source-command-coordinator.test.ts`) already contains sharp, targeted tests for exactly this ("rolls back a local mutation when saving its public receipt fails", "resolves uncertain commands with audit, exact replay and no task mutation, including after restart", "fences late preparation after core recovery records non-application", "times out a provider that ignores cancellation and never applies its late plan") and all pass against HEAD. I traced each of these tests by hand against the implementation rather than taking them on faith.
- **Financial totals.** `usage-service.ts`'s `totals()` correctly ignores a run's legacy `run.costUsd` the moment any per-event usage record exists for that run (confirmed by hand-tracing the "mixed" fixture in `usage-service.test.ts`), and only reports `knownCostUsd` when *all* events for a run have a known cost, vs. `observedCostUsd` for any known-cost subset — this is intentional and correctly test-covered, not a bug. `pricing/standard.ts`'s `estimateRecord` correctly rejects `cachedInputTokens > inputTokens` and non-Codex/unknown models (returns `null`, excluded from aggregate rather than silently coerced to 0). `outcomes.ts`'s `aggregateOutcomes`: (a) day-bucketing is correct even for a non-midnight `from`/`to` window — proved by hand (any `startedAt` in `[start,end)` always maps to a day bucket already present in the generated `days` Map) and confirmed by an executed probe with a `13:00Z`-anchored window spanning parts of 3 calendar days; (b) `costPerPublishedPrUsd`/`costPerReviewedPrUsd`/`costPerMergedPrUsd` divide total cost by the count of *distinct* PRs, not by run count, so multiple runs linked to the same PR number correctly average down to a true per-PR cost rather than inflating the denominator — confirmed by probe (two runs, one PR, cost 4+6 → `costPerMergedPrUsd === 10`, i.e. divided by 1 PR not 2 runs); (c) merging duplicate PR-availability records (`known` vs `stale`/`unavailable`) for the same `(repo,number)` is order-independent — `known` always wins regardless of arrival order — confirmed by probe running both orderings and asserting identical output.
- **SDK contract / alternate providers without hidden assumptions.** I compared the Jira (`src/plugins/jira/provider.ts`) and Todos (`src/plugins/todos/provider.ts`) implementations against the shared `TaskSourceProviderV1` contract (`src/plugins/tasks.ts`) and the shared `SourceCallContextV1`/activity-read helpers (`src/plugins/activity-read.ts`). Both providers are self-contained: neither leaks Jira- or Todos-specific types into `task-source-service.ts`, `task-source-schedule.ts`, or `task-source-adoption.ts`, which only ever touch the generic `TaskSnapshotV1`/`WorkRefV1`/`SourceMutationPlanV1`/`SourceIdentityEvidenceV1` shapes. The one place a provider gets special-cased at all is `LocalSourceAdapter`'s `storageLayout` field (`'documents'` vs `'legacy-todos'` vs `'remote'`) in `task-sources/local-records.ts`, which is a storage-backend detail for the two shipped local-record implementations, not a leak of provider identity into command/scheduling/adoption logic — a genuinely new third-party local-record provider would use `'documents'` layout and receive identical treatment to Todos. The scheduling policy (`src/plugins/scheduling/provider.ts`) only consumes the generic `SchedulingCandidateV1`/`SchedulingSourceV1` shapes and defensively re-validates every field of an untrusted page before trusting it, so it works uniformly across providers.

### Tested negatives (explicitly attempted to break, did not)

- Duplicate `externalId` across two sources → no cross-contamination (probe).
- Non-advancing / repeating / duplicate-item pagination cursor from a provider → rejected (probe + existing Jira/Todos provider code paths).
- Source/scope/collection-identity changing between the start and end of a multi-step read → rejected (probe).
- Losing the outer receipt write after a local mutation actually committed ("uncertain receipt") → recovered via `hasCommandResult`, not silently dropped nor double-applied (existing coordinator tests, hand-traced).
- Retrying an identical vs. a subtly-modified command under the same `requestId` → identical retries replay the exact stored receipt; modified retries throw `'content changed'` (existing coordinator tests).
- Disabling a source instance mid-flight, then replaying an already-settled command → replays the frozen terminal receipt rather than re-executing (existing coordinator test: "atomically creates, moves and deletes ... and replays terminal results after disablement").
- Financial aggregation with non-midnight windows, PR-duplicate-order sensitivity, and PR-vs-run cost averaging → all produced correct, order-independent results (probes).
